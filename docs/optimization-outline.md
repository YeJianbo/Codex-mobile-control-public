# 控制台优化大纲

更新日期：2026-10-23。范围：Gateway、AgentHost、Web、Android 及 QQ／微信入口。

本文记录下一轮优化方向和完成标准，不表示以下项目已经实现。依据是当前控制台结构及对 dsh-cliworker-now 0.8.2 的源码对比；尚未进行两者的性能对测。既有功能和历史修复记录继续以 `work-status.md` 为准。

## 1. 优化目标

以正在建设的小助理 Agent 为上层入口，让不同入口共享可靠的会话、执行状态和统计，让不同 Harness 保留原生能力，并为小助理补齐跨 Harness 子代理调度。优先解决断连、串会话、重复消息和统计来源问题，随后扩展调度，最后扩展执行器种类。

本轮规划沿用已有 Gateway、AgentHost、Codex 共享后端及 SQLite；已有回执、队列、审批、事件回放和适配器原位演进。结构调整前保留可回退版本与必要配置备份，不复制凭据到公开文档或发行包。

## 2. 目标结构与职责

```text
Android / Web / QQ / 微信
              │
              ▼
Gateway：认证、入口路由、发送回执、会话查询、事件持久化
              │
              ├── 现有小助理：理解请求、拆任务、选择执行器、跟进与汇总
              │        │
              │        └── 协作调度：父子任务、选型、排队、资源占用、结果回传
              │                 ├── Codex 适配 → 现有共享 app-server
              │                 └── AgentHost → 各 Harness 原生协议及进程
              │
              └── 管理接口 → Local Console：账号、路由、额度、统计、更新
```

协作调度先作为现有服务内的模块实现，现有助理通过服务工具调用它，普通聊天仍可直接使用 Harness。执行进程继续由原所属后端管理；客户端只发送操作、消费状态，不各自推导任务是否运行。重构边界由实际职责确定，不为了统一名称搬动所有文件。

### 现有小助理的承接方式

当前 `PersonalAssistant` 已有任务、执行器适配、回执、历史、审批和停止操作；`GatewayAssistantAdapter` 复用网关任务入口，`AssistantEngine` 有独立模型循环及文件／命令工具。它们提供了基础，但当前已读取的工具表没有跨 Harness 的子代理派遣、等待与结果收取能力，不能将现有任务入口等同于完整协作。

- 小助理负责理解用户意图、决定是否委派、组织依赖和汇总结果；调度模块负责身份、队列、取消和持久化；Harness 负责实际工具执行与原生会话。
- 小助理模型与子代理 Harness／模型分别配置，保留用户当前小助理选型。增加子代理能力不自动替换主模型，也不让主模型供应商限制执行器选择。
- `PersonalAssistant` 与自有 `AssistantEngine` 接入同一个调度服务，避免为每个助理执行器重复维护任务队列。模型可调用的工具还须按实际 Harness 的扩展能力接入；后台已有接口不等于 AGY 等主模型已能调用。
- 小助理普通聊天不强制用户选择项目。需要项目操作时，子任务明确绑定已有授权目录；目标不明确时才询问，沿用渠道独立助理空间，不凭历史挑选其他项目。

## 3. 第一阶段：会话与连接正确性（P0）

### 会话身份与发送目标

- 区分界面当前选中会话、请求实际目标会话和 Harness 原生会话；发送时固定目标，异步回调不能重新读取当前选中项作为发送目标。
- 沿用现有 requestId 与回执，把发送、排队、取回编辑、续聊的身份关联收敛到同一条路径。
- 主聊天和侧边聊天各自保存选中项、草稿与加载请求；旧请求只更新所属会话，不能切换当前页面。
- 已有原生会话恢复失败时保留原身份和消息，提供明确的恢复或新建操作。

### 连接与恢复

- 核对已有 URL／token 变化检查、关闭处理及重连互斥，找出仍绕过这些路径的调用。
- 前后台切换、内外网切换及手动重连复用同一个连接协调入口；取消旧尝试，避免并行握手和迟到回调覆盖新连接。
- 先恢复连接和当前会话状态；历史补齐、模型目录、额度和统计按需读取，不阻塞发送就绪状态。
- 区分网络中断、Gateway 重启、AgentHost 重启和上游失败；按实际来源恢复，沿用发送回执确认结果。

涉及模块：`sessionManager.ts`、`receiptStore.ts`、`codex/appServerClient.ts`、`agentHostProtocol.ts`，以及 Android／Web 连接和会话状态模块。

完成标准：发送目标不随界面变化；后台事件不抢当前会话；端点变化后连接正确后端；重连不重发已接收消息。现存机制已满足的部分保留，只修改发现的缺口。

## 4. 第二阶段：统一执行状态与能力（P0）

- 明确会话、运行轮次、原生会话、工具调用、审批的身份关系；沿用已有字段，只有缺失且确有用途时才补字段。
- 梳理排队、启动、执行、等待回答／审批、停止中、完成、失败、中断的状态转换，服务端负责发布真实执行状态。
- 页面加载与任务执行分开；正常流结束、CLI 退出、上游重试及真实失败按各协议判定。
- 整理每个 Harness 的能力：图片、文件、公开思考、规划、运行中引导、排队、提问、审批、恢复、分支和上下文数据。
- Web 与 Android 从同一份能力信息生成操作入口，保留各平台适合的交互。
- 保留现有用户审批策略；统一审批事件和归属，不把其他项目的拒绝规则或权限开关直接移植过来。

涉及模块：`agentSessions.ts`、`agentProtocol.ts`、`harnessAcp.ts`、`claudeAcp.ts`、`agyCli.ts`、`grokAcp.ts`、`remoteAgentSessions.ts` 和两端状态消费代码。

完成标准：相同任务在各端的状态与可用操作一致；停止未完成时保持停止中；不支持的能力有准确呈现，已支持能力不被统一层削弱。

## 5. 第三阶段：跨 Harness 协作调度（P1）

### 小助理的委派闭环

- 提供派遣、查询、续聊、停止以及按事件等待／读取结果的工具，交给现有小助理调用。展示层和模型工具复用服务操作；不要求模型通过 shell 手工启动受管 CLI。
- 先支持直接完成、单任务委派和少量独立任务并行；存在依赖时前一任务完成后再启动下一任务，由小助理汇总交付。
- 首个落地范围选择已有 Codex 和 AGY 适配：同一助理会话派出不同执行器，保留独立子会话，按原生身份继续执行，再逐步覆盖其他 Harness。
- 子任务完成通过事件唤醒对应父任务，按父任务、子任务和运行轮次去重；沿用回执恢复进度，避免持续轮询或恢复后重复派遣。
- 返回结构化状态、简短结论和产物引用；完整过程留在子会话，按需展开，避免把全部工具日志重新塞入小助理上下文。
- 子任务失败由小助理依据实际错误决定继续、调整或请求用户处理；不同执行器的权限及用户授权继续有效。自动重试沿用现有策略，结果未知的写操作先核对状态。
- 区分关闭面板、停止单个子任务和停止整个助理任务；整体停止先撤销待派遣项，再对其拥有的活动子任务发起停止并等待确认，不影响用户另开的会话。

### 任务与智能体

- 在已有助理任务和子会话关系上补齐命名智能体、角色预设、父会话归属、续聊与结果回传。
- 任务保存创建时的 Harness、模型、思考强度和角色；后续按已选配置执行，允许用户明确修改可修改项。
- 提供派遣、状态、续聊、停止四类操作，人工点击与模型调用复用同一服务入口。
- 优先完成主会话到直接子任务的协作；需要管理 Harness 自己产生的后代任务时，按原生能力接入。

### 并发与目录占用

- 增加可配置的跨 Harness 并发预算，继续复用现有会话队列和发送回执。
- 对调度器管理的同目录任务，写任务与其他访问冲突时串行；只读任务按并发预算运行。首版可采用目录级读写互斥。
- 等待任务显示具体原因，例如等待执行名额或工作目录占用；停止后确认受管执行已结束再释放占用。
- Codex 桌面端或用户另外启动的 CLI 不一定经过调度器，界面和文档准确说明协调范围；不能据此声称目录已被全局锁定。
- 如需提高同项目写任务吞吐，再按实际需求评估独立 worktree，合并继续由明确操作触发。

涉及模块：`personal-assistant.mjs`、`assistant-engine.mjs`、`agentSessions.ts`、`agentHost.ts`、`subagentThreads.ts`、现有队列服务及父子会话接口。

完成标准：小助理能够按需派遣不同 Harness，查看并停止任务，按同一身份续聊，接收对应轮次的结果并汇总给用户；受管写任务不同时争用同目录。关闭任务面板不等于停止或删除任务。实际选用的主模型必须完成一次真实的委派与结果回收验收，不能只验收人工点击或模拟工具。

### Codex 扩展入口：调用其他 Harness 作为外部子任务

将同一套调度能力封装成 Codex 插件，由技能提供委派规则、MCP 提供执行工具。这样现有小助理和 Codex 主会话都可以使用我们的 Harness 适配，不再各维护一套执行后端。

已核对本机 Codex CLI 为 `0.162.0-alpha.17.2`，具有插件管理命令。官方文档支持插件组合技能与 MCP；自定义子代理继承父会话的 provider、MCP 和权限，自定义 agent 文件不能覆盖 provider。本次未找到公开的外部子代理执行器注册接口，因此不能仅把角色文件中的模型名改成 Gemini／Claude，就接入这些 CLI 的原生账号、工具和会话。

建议首版结构：

```text
Codex 主会话 ── 插件技能 + MCP 工具 ─┐
                                   ├── 共享协作调度服务
现有小助理 ── 服务工具 ─────────────┘          │
                                              └── 现有 Gateway / AgentHost
                                                        └── AGY / Claude / 其他 Harness
```

- 工具涵盖可用执行器目录、派遣、查询、续聊、有限等待、结果读取和停止；启动返回任务标识，长任务继续由已有后端管理，避免把一次 MCP 请求挂到整个任务结束。
- 首版优先本机 stdio MCP 桥接现有认证网关；扩展本身不保存账号凭据、不直接拉起另一套受管 CLI。插件断开不自动终止已提交任务，重连按回执查询。
- 派遣明确选择 Harness、模型、任务和目录；复用原生账号与工具，任务保留原生会话身份，完成后可继续。小助理与 Codex 都读取同一份真实任务状态。
- Codex 官方子代理列表是否支持直接展示外部任务尚未建立依据。首版由 MCP 返回状态与任务链接，在我们的 Web／Android 展示完整过程，不伪造 Codex 原生子线程。
- 如需原生子代理入口，可单独验证一个 Codex 自定义角色调用 MCP 的代理模式：原生子线程负责调度，真正执行留给外部 Harness。该模式仍产生 Codex 调度用量，停止代理线程也不天然等于停止外部任务，必须补齐所有权和取消关联后再采用。
- MCP 启动的外部 CLI 不自动继承 Codex 沙箱。接入必须按客户端会话绑定、目录授权与现有审批策略约束操作；不能相信模型自填的父会话 ID，也不能把允许调用工具视为所有子任务操作已获批准。无法落实请求的权限范围时先返回能力限制。
- 首个交付目标：Codex 通过插件派出一个 AGY 任务，读取结果，再用同一外部会话续聊或停止；不修改官方 Codex 二进制，不重启共享后端来完成安装验证。

参考：[Codex 子代理配置](https://learn.chatgpt.com/docs/agent-configuration/subagents)、[插件结构](https://developers.openai.com/plugins/concepts/plugins)、[插件打包](https://developers.openai.com/plugins/build/plugins)。以上是设计方案，尚未实现插件或验证原生子代理代理模式。

## 6. 第四阶段：账号、原生协议与统计（P1）

### 账号与模型路由

- 明确执行所用账号、提供方、端点、模型和原生会话的关联，账号／路由切换后失效对应目录缓存。
- 续聊前识别影响原生会话恢复的账号变化；按该 Harness 实际约束处理，保留可恢复历史。
- 继续支持官方账号与用户配置的中转；账号绑定规则同时覆盖这两类来源。
- 健康检查、版本检查、模型目录与额度查询分别缓存并合并并发请求；普通会话打开不触发整套探测。

### 协议选择

- 保留 Codex 共享 app-server、AGY stream-json 及当前有效适配。
- 优先对现有 OpenCode／Hermes ACP 的具体问题，比较其 HTTP＋SSE／Runs API 的恢复、取消、事件完整性和进程成本。
- 只有原生通路能解决已定位的问题才迁移；旧会话按兼容能力恢复，保留创建时所需协议和原生身份。
- 新增 Kimi、Pi、OMP、MiMo、ZCode、Qoder 等执行器放在核心稳定后，按实际需求选择。

### 用量与速度

- 分开保存本轮账单、会话累计、当前上下文、账号额度；记录来源和缺失项，避免相互代用。
- 逐条请求区分排队、启动、首字等待、生成、重试及总耗时；仅有轮次汇总时按轮次显示，不能伪称单次上游请求。
- 速度使用有明确来源的输出 token 和对应生成时长；不足以计算时保持未知。
- 分别记录用户选择的 Fast、实际请求参数及上游确认结果；只有来源确认时才能按实际 Fast／普通请求分组。
- 金额沿用提供方价格规则并标明估算；不同口径的 Web／Android 统计只在相同会话和时间范围内比较。

完成标准：模型配置、实际执行来源和统计能关联；缺失指标不补造；账号切换不会继续显示旧账号目录或额度。

## 7. 第五阶段：性能与多端交互收敛（P1）

- 事件按会话与轮次更新，控制流式刷新频率，避免一个会话更新导致整个列表和后台统计重算。
- 保留工具、命令和更改详情展开后加载；完成态继续使用已恢复的外层过程、内层操作折叠。
- 长历史继续分页，限制驻留内容和重复解析；保持滚动锚点，不因补历史、摘要或状态变化跳动。
- 后台会话优先更新状态，选中后加载正文；模型发现和统计扫描使用已有后台机制并设并发预算。
- 管理页按模块加载；聊天、设置和统计共用数据口径，页面尺寸、触控与玻璃效果按平台调整。
- 子任务运行时突出，空闲后回侧栏；完成通知遵循当前前台和会话规则，目标页面从任务身份定位。

完成标准：首次操作不跳顶，未展开详情不加载，后台更新不抢焦点；性能改动以相同条件下的结果判断。没有真机采样时只报告代码路径变化和本地结果，不声称真机卡顿已消除。

## 8. 实施顺序与验证

| 批次 | 交付内容 | 依赖 |
| --- | --- | --- |
| A | 会话身份、发送归属、连接恢复缺口清单与修复 | 当前代码及已有日志 |
| B | 执行状态、能力目录、两端操作一致性 | A |
| C | 账号来源、统计口径、探测缓存整理 | B；可分模块实施 |
| D | 现有小助理接入子代理工具，完成 Codex／AGY 派遣、续聊、停止、结果回收；再扩展命名角色与目录占用 | A、B；使用 C 的来源信息 |
| E | 长历史、按需加载及多端交互收敛 | 各批次随改随做 |
| F | 需要迁移的原生协议与新增 Harness | 对应已定位问题及兼容证据 |

每批只重构相关模块，保留既有功能和无关修改。先完成受影响构建及仓库要求的检查；已知回归或具体失败信号再增加针对性检查，不重复运行无新信息的验证。

涉及真实模型请求、活跃任务中断或设备操作时单独安排实际验收。通过构建、模拟服务或只读握手不能替代真实生成、恢复和停止验收。交付记录实际完成、未验证部分及最小人工检查步骤。
