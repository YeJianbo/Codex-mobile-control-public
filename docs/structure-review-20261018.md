## 结论

需要优先处理的是模型身份规则、配置持久化、提交记录生命周期和异步状态归属。当前问题不是缺少抽象，而是部分领域有多个事实来源，同时入口文件承担了过多业务职责。建议沿现有单进程架构按领域整理，不重写全部客户端、不引入通用大框架。

下面的“确定”指已从代码确认行为或结构；只有明确说明的项目才代表运行复现。第一至六节为封存基点的静态检查；首批与后续测量、处理决定分别见第七、八节。

## 三、真正可以减少的过度防御

1. **猜测式补全**：空目录生成假定能力、多处用模型名称猜品牌/执行器/默认强度。用明确的数据字段替代，而不是继续叠加例外正则。
2. **重复状态和重复检查**：提交入口、回执 facade、执行器之间重复持有状态；连接保护也有局部手写重复和漏用。合并事实来源，复用现有机制。
3. **同一路径层层格式猜测**：模型显示中多次截断 ` · `、`::`、`/`。显示、路由和身份分离后，只处理已知格式，未知名称原样显示。
4. **没有真实输入变化的重复断言**：`build-release.py` 新建 TemporaryDirectory 后，反复比较刚构造的固定 stage/work 子路径；未创建的 stage 先检查删除。可以减少局部冗余。实际递归删除边界、压缩包完整性、签名及依赖校验仍应保留。
5. **已退出产品路径的旧实现**：S08 的旧 VM、旧 WebView 资源及专属脚本，确认无消费者后一起移除，避免留下半套无入口系统。

“无条件 catch 后继续”不是应保留的健壮性。F03、F06、F07 需要正确表达错误和取消；也不应反过来为所有函数新增通用校验层。

## 四、性能候选：先测再决定

| 候选 | 已确认的代码路径 | 需要的最小证据 | 可能的处理 |
| --- | --- | --- | --- |
| 模型目录被慢来源拖住 | 聊天入口 Promise.allSettled 后才返回；助理入口已有预算与缓存策略。 | 冷/热目录读取耗时，逐 Harness 耗时，切回前台的关键请求链。 | 共享成功缓存、并发合并及增量状态；避免等待不相关 Harness。 |
| 事件写入占用事件循环 | 每事件同步 SQLite BEGIN/归档/INSERT/trim/COMMIT。 | 多会话流式输出时事件循环延迟、事务耗时、心跳延迟。 | 必要时有界合批或调整持久化执行位置，保持事件顺序和恢复一致性。 |
| 慢客户端发送积压 | `EventHub.sendPayload` 检查 OPEN 后直接 send；bufferedAmount 只用于诊断。 | 多开与弱网下 bufferedAmount、进程内存、广播延迟。 | 有界发送与明确恢复策略，不能静默丢失流式文本。 |
| Android 根状态更新过宽 | 多个业务域共用 NativeViewModel.state 与根 UI。 | 具体交互的重组、布局和绘制耗时；区分玻璃绘制与状态更新。 | 按领域缩小订阅及热路径更新范围。不能单凭文件大小判断掉帧原因。 |
| HTTP 客户端归属不清 | 每个 GatewayClient 创建 OkHttp owner，再派生 connectionTransport；有 WebSocket/请求取消。 | 多次切电脑、探测、前后台后连接池、线程和存活实例是否持续增长。 | 明确 owner 与复用边界；认证、证书和 pin 隔离不能被连接池共享破坏。目前未证实泄漏。 |
| 回执全量序列化和事件扫描 | CommandReceipts 每次变更序列化全表；MessageSubmissions.status 复制并反转事件查找。 | 回执随使用增长后的写入耗时；状态轮询频率与事件量。 | 逐条持久化及按 requestId 查找，合并回执领域时一并处理。 |

这些测量用于确认具体瓶颈，不建议再建长期 benchmark 平台或为本轮添加门禁。

## 五、应保留的设计与防护

- 连接代际、取消、迟到回包隔离；共享 app-server 的 URL **和 token** 端点变化检查。本轮源码中仍有检查，不应为精简重连代码删去。
- requestId 幂等、执行结果 uncertain、未知提交不自动重发、队列取回编辑的持久化交接。它们解决真实重复发送与丢草稿问题。
- 操作和 diff 展开后才加载：Web `lazyActivityDetails` / `renderActivityWhenOpen` 等路径应保留。移动端相同约束也应列入后续行为对照。
- 历史增量、索引、worker，以及 ParsedEventHistory 的共享内存预算。缓存复杂不等于无用。
- 公网认证、设备签名与防重放、TLS pin、管理桥 DTO 白名单、私钥本机边界、项目白名单及 realpath 符号链接约束。读取了相关入口，没有把必要的访问控制归为“过度防御”；本轮不构成完整安全测试。
- iOS 复用 WebKit 的现有边界是合理选择。没有证据支持为结构统一而改成完整原生实现；本轮未做 Xcode 编译及真机检查。
- 现有单进程 Gateway、按 Harness 的适配器、平台专属 UI。目标是共享事实和领域规则，不强行共享所有渲染实现。

## 六、建议的分批顺序

| 批次 | 内容 | 不可退化的行为 |
| --- | --- | --- |
| A：正确性 | F01/F02 模型身份与显示；F03/F04 配置更新；F06 连接状态归属；F07 事件失败处理。 | 原始模型 ID、跨品牌名称、路由、账号配置、连接隔离、可恢复历史。 |

| C：清理与拆分 | S08 旧代码；S02/S03/S04 按领域抽模块；S09 随对应模块迁移测试。 | 现有入口、长按菜单、折叠层级、懒加载、滚动位置、主题即时切换、草稿。 |
| D：目录与热点 | S01/S07/F08 完整归一模型目录；按最小测量处理确实存在的性能热点。 | 已选模型、真实能力、失败时保留成功目录、不同 Harness 的协议边界。 |

建议先做 A，再做 B；C 中清理无入口旧代码可独立进行。涉及大状态与提交域的重构分别交付、分别对照，不同一批同时改协议、UI 和持久化格式。

用户原始约束是功能及性能不得退化，因此 F01-F08 的行为修正与纯结构移动要分开记录，不能借“重构”悄然改变默认值或路由。后续每批先编译/构建，只在涉及已知回归或具体失败信号时运行对应验证，不反复跑无关全量测试。
